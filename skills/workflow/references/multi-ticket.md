# Build an agreed feature through one integration PR

The active Orca conversation coordinates Orchestra Auto. The developer's build request ends with one open integration PR. Use the repository, assignment overrides and routing policy from this conversation. In the commands below, `<helper>` is the absolute path to this workflow's installed `scripts/ticket_flow.py`. Keep run records, briefs and check reports outside all worktrees.

## Start at the agreed spec

1. For a build from an idea, complete the design and publication steps in the main workflow and use the verified issue immediately. For a build naming an agreed spec, read the existing issue and comments. Reuse existing tickets and their decisions. New product or scope questions go to the developer in this original conversation. Relay the answer to the relevant worker with the Orca reply mechanism and record which artifact it changes.
2. Run `python <helper> begin-feature --repo OWNER/REPO --spec SPEC`. Save the returned ticket-map flow ID alongside the Orca Run ID and any preceding design-only flow ID. Follow the installed Orchestra Auto skill, routing, preflight, long-horizon, dispatch, ledger, acceptance and closeout references. Follow the platform/session binding and worker verification steps in [single-ticket delivery](single-ticket.md). Use the upstream flow's acceptance and invalidation records at each gate.
3. By default the CLI hosting this conversation runs ticket planning. The implement and review defaults apply to their respective worker dispatches. Keep the ticket-map decision here when a separate planning CLI is assigned. Read `engineering/to-tickets/SKILL.md` under `MATT_SKILLS_ROOT`. Apply its tracer-bullet breakdown to the published scope. Present the proposed granularity and genuine blocking edges for the developer's ticket-map decision here. A previously approved map proceeds directly to verification. Keep the original spec agreement. Publish each new ticket once as a child of the spec with the project's triage label and dependency links. Use the tracker's documented textual fallback where necessary. Verify the full set of child issues and blocking relationships, including paginated results. Record the verified map, spec and decision for Orchestra Auto's G-tickets gate.
4. Save the verified graph as UTF-8 JSON, for example `{"7": [], "8": [7], "9": []}`. Keys are **all** implementation ticket numbers for this spec. The arrays contain the tracker numbers that block each ticket. Resolve external dependencies only in the named repository. If a blocker belongs to another repository or the tracker map is incomplete, resolve it in the conversation before dispatch. Keep this map tied to the gate evidence. Reconcile changes to the tracker before each dispatch wave and update the recorded map if the scope changes.

## Work the dependency graph

Use Orchestra Auto's long-horizon assignment: one top-level integration worker on the resolved implementation CLI. Dispatch via `<helper> dispatch --step implement` with the normal preflight, routing, intent, unique request, isolated worktree, start verification and receipt. Give the integration worker Matt Pocock's `engineering/implement-spec` and `engineering/tdd` skills, the map and spec, the implementation assignment(s), checks and integration branch. Specify the separately assigned final review in its brief. Its implementation ownership ends at the tested integration handoff.

- Require the upstream nested isolation proof before starting tickets. Use a fresh isolated implementer and branch off the current integration tip for each ready ticket. Check that the assigned CLI and routing profile apply to every model-bearing worker. If a nested worker cannot prove its assignment, route or isolation, use the upstream per-ticket Orca worker alternative, record the change and respect the upstream concurrency cap. Use the shared dispatch helper for those Orca workers. The coordinator tracks outstanding claims in the Orchestra Auto ledger to prevent duplicate dispatch when independent tickets finish concurrently.
- Start the UTF-8 test report with `{"checks":[]}`. Run `python <helper> frontier --repo OWNER/REPO --map-file <map.json> --tests-file <checks.json> --head <full-current-integration-SHA>` in a checkout with the integration and ticket objects. Dispatch unclaimed tickets in `ready`. The helper checks the Git ancestry of each tested commit and reads any external same-repository blocker's issue state. Issue state alone cannot release a child in the map.
- Each implementer applies TDD at the agreed seam, brings the current integration tip into its branch, runs the ticket's checks on that final commit and returns the commit, command, result and durable log for each check. The merger integrates passing work in the integration worktree, preserving tested SHAs by merge or fast-forward. Verify actual check output, worker identity and settlement in the transcript/CI. Add the ticket's rows to the report after its tested commit is reachable on the integration branch. Rerun `frontier` at the new tip. In-map blockers can now release dependents even while the corresponding GitHub issues remain open. Preserve failed attempts in the ledger, repair the owning ticket and rerun its checks before recording passing evidence.
- After the first integration merge, create or reuse the one draft PR from the integration branch to the agreed base. Include GitHub `Closes` links for the spec and tickets. Use this PR for all further pushes and review cycles. Individual ticket workers return commits and logs to the integration worker.
- After every mapped ticket is integrated, run the combined suite on the actual final head. Save its full SHA as `head` and its commands, passing results and log references as `integration` in the same report. The abbreviated example below shows the JSON shape. Use full 40-character Git SHAs and observed evidence for every ticket and check.

```json
{
  "checks": [
    {"ticket": 7, "commit": "<tested-ticket-7-SHA>", "command": "make test-filter", "result": "pass", "evidence": "<ticket 7 log>"},
    {"ticket": 8, "commit": "<tested-ticket-8-SHA>", "command": "make test-export", "result": "pass", "evidence": "<ticket 8 log>"}
  ],
  "head": "<tested-integration-SHA>",
  "integration": [
    {"command": "make test", "result": "pass", "evidence": "<complete suite log>"}
  ]
}
```

## Review and return the integration PR

1. Spot-check at least two distinct tickets' actual evidence as required by Orchestra Auto. Verify the integration worktree is clean and the PR points to the tested integration SHA. Fetch the PR's base and head into the coordinator's checkout. Run `python <helper> review-brief --repo OWNER/REPO --pr PR --spec SPEC --map-file <map.json> --tests-file <checks.json>`. This gate checks all expected ticket results, blocker ancestry and integration evidence. It supplies the actual diff range, spec, every ticket and the two levels of check evidence.
2. Record implementation acceptance at that head. Dispatch the **assigned review CLI** once for the combined change in a fresh top-level worktree based on the returned head. Follow the validated brief, routing, receipt and identity steps in [single-ticket delivery](single-ticket.md). Give it the returned packet, relevant decisions from the original conversation and installed `engineering/code-review` skill. Verify its standards and spec verdict against the actual assigned dispatch, base and head. For requested changes, send the findings to a fresh implementer on the integration branch, rerun affected ticket checks and the integration suite, recheck dependent tickets against any newly tested blocker commit, refresh the evidence, invalidate stale acceptance and repeat review on the same PR.
3. Use `evidence` then `verify-pr` as in single-ticket delivery, replacing `--ticket NUMBER` with `--map-file <map.json>` in both commands. Preserve the PR description and closing links when updating its evidence. Mark the existing PR ready before final verification. The helper checks that the integration branch has one open, ready PR for the reviewed base and head.
4. Return the verified link, tested/reviewed SHA, per-ticket and integration checks, and reviewer findings here. Record `pending_type: human_merge`, settle and release worker resources through upstream closeout. Report the observed tracker state. The developer owns the merge.
